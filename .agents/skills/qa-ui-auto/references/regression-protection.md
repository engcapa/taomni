# 保护既有行为

用于改变既有行为、共享组件/状态或 UI 交互的开发与验证。维护 skill 文档时只检查这些规则，不启动产品盘点。配合 [高效验证选择](efficient-verification.md)，将回归范围收敛到受影响的行为；精确选 case 不代表这些 case 已充分覆盖影响。

## 改之前确定保留什么

在本次设计、卡片或交接中复用 AC/V ID，区分新增、有意改变和必须保留的行为。UI 重构授权允许改变布局与流程，不自动授权移除已有能力、吞掉错误或丢失数据。对齐依据未涉及的 Taomni 能力不能因 IDEA 没有同样入口而被删除。

把“保持现有功能”具体到用户动作和结果：受影响入口/调用方、保留的结果与副作用、适用状态、对应测试、改前依据和改后结果。简单改动可以是一段话，不另建全量功能清单或强制单独文档。新建/细化任务时，把相关保留行为纳入本卡验收；不能只有新功能 AC。

沿生产调用方、事件注册、store 订阅、样式作用域和 IPC 消费者追踪影响。不能用“只改一个文件”或 case 的 `covers` 在当前 feature 内，推断影响只在本卡。下表是选场景的提示，按真实调用和本次变化选择，不是每次必跑清单：

| 改动边界 | 应检查的既有行为 |
|---|---|
| 快捷键、Action 路由、菜单、焦点 | 受影响入口执行同一动作；输入框/终端的按键不被抢占；Esc 关闭后焦点恢复；动作只触发一次 |
| 编辑器实例、extension、tab/store 同步 | 编辑后的 dirty/save、undo/redo、切换文件再返回、多个编辑器隔离、只读；重挂载后无重复订阅或历史丢失 |
| 弹层、portal、全局 CSS、公共布局 | 相关消费者的点击命中、遮挡、滚动、键盘可达和选中/失焦状态；至少覆盖实际受影响的不同使用方式 |
| 异步 provider、请求/结果状态 | A 请求中切到 B，A 的迟到结果不污染 B；取消、失败后原流程仍可继续 |
| 共享 IPC、持久化、文件/会话操作 | 既有调用方的默认值、错误处理与真实效果；已有数据仍可读写，失败/取消不产生未声明副作用 |

共享契约改变时逐一核对消费者，按相同行为等价分组执行代表性场景；不同参数、生命周期或错误分支要单独覆盖。检索不到消费者或映射不完整是待解风险，不能据此缩成只测新功能。

## 建立有用的改前基线

在修改行为前先检查已有测试是否真实断言上述结果。高风险、缺少覆盖的既有正常路径，先补最小行为回归并在改前确认通过；缺陷修复另有能暴露原错误的失败测试。这两类测试分别证明“旧行为继续正常”和“缺陷被修复”，不能互相替代。纯样式/文案等低影响修改可用渲染和操作观察，不为凑基线编造单测。

优先复用匹配改前源码、case、配置和环境的有效证据；缺失时只运行所需的低成本基线。只有原生边界才能区分时才补原生探针，不要求每张卡前后各编译一次。旧二进制可以证明它所绑定的旧源码，不能冒充当前改前状态。

记录基线源码身份，包含相关未提交变化；HEAD 本身不够。如果代码已改，使用保留的改前材料或隔离检出做必要对照，不在当前工作区强制回退、覆盖用户改动来制造基线。无法重建时明确“改前未知”，加强当前契约检查，不声称已证明前后无退化。

基线也失败时核对 fixture、服务、配置和期望。只有有依据的改前失败才能标为既有问题；候选新增失败或加重失败仍需处理。既有失败若阻断本次验收，就不是可忽略的背景。基线结果作为比较依据保存，不写成候选源码的当前通过证据。

## 开发时同时保护两组断言

本轮验证集合是“目标变化的验收 + 受影响的保留行为回归”的去重并集。只验证新入口成功，不能证明此前入口、退出/恢复和其他消费者继续可用。

交互/共享行为重构按可验证的边界推进：先保留原行为与数据契约，再切换新布局/动作接线，每完成一个有实质风险的边界就运行受影响的快速回归。最后检查最终组合代码上的相交行为，不能把各自孤立通过的结果当作集成通过。不强制每段提交或每段原生构建。

优先使用生产入口与真实状态变化做断言；mock 只替代当前层无法访问的外部边界，不 mock 掉正在重构的路由/状态机来证明它正确。对事件和生命周期改动，包含与风险相符的连续操作，例如“打开→执行→关闭→再打开”或“编辑 A→切 B→返回 A”，避免只有全新实例上的一次成功。挂载和浏览器覆盖不能替代受影响的 OS 行为。

审查测试 diff：删除、跳过、放宽断言、更新快照或替换 fixture 都要对应明确的期望变化。有意替换 UI 时可更新 selector 和目标画面，但保留结果、副作用与恢复断言；不能把失败后的当前输出自动设为新期望。新增的弱测试不能代替原有更强的检查。

## 发现回归后怎样收尾

本次改动引入的退化属于当前任务的修复责任，即使发生在另一个 feature、旧卡或共享消费者；“相邻问题不在范围”仅适用于独立的既有问题/新增需求。先停止继续叠加同一路径的变化，缩小复现并修复本次原因；必要时只撤销自己的相关变更，保留他人工作和数据。确有新的产品范围/兼容取舍时，提供具体方案再讨论。

修复后跑暴露退化的检查和受修复影响的相邻检查，再完成本轮尚未满足的验收。按输入/模式复用构建，把目标与保留场景合并为必要的 native 批次；不要靠反复全量运行等一个绿结果。

交付分别说明目标验收、保留行为回归、已知基线失败/缺失和实际平台证据。已知本次引入的回归未解决，不能标为完成；关键保留行为未验证，要明确为证据缺口。仅当目标和所选保留契约均满足时收尾。一次回归修复留下能暴露该失效机制的最小持久测试，并更新受影响的 case/映射，不无条件扩大全 App smoke。

`plan` 的文件映射、`status` 的选中用例通过和任务板的结构校验都不能自动证明回归集完整。完整性来自上述影响分析与断言审查；工具报告的通过仅限实际选择和执行的范围。
