# UI 与交互对齐

## 目标约束

“基于当前功能”要求利用已有正确能力，不要求冻结现有外观、信息结构或操作流程。可以调整或替换组件、拆分大组件、重做布局/菜单/弹窗/面板与交互状态机。需要大改时按独立可验收的用户场景分段交付，保持功能可用和数据可恢复，不为完成卡片数保留已证实不合适的 UI。

复用当前 Action、数据和事务契约是起点；若目标要求改变这些契约，明确新旧行为、迁移与回归范围，而不是绕过统一动作或建立重复状态。历史文档中的“沿用现有 UI”只约束其原任务，不是新 UI 改版的产品禁令。

## 场景规格

从 `idea-reference` 的观测提炼以下适用项，避免凭记忆设计成另一个编辑器：

- 窗口/面板比例、标签和树行密度、工具栏、边距、边界与溢出。
- UI/代码字体、行高、图标、色彩层次、选中与失焦、禁用与悬停。
- 菜单/候选列表/说明面板的位置、锚点、遮挡处理和边缘翻转。
- 鼠标与键盘入口、焦点转移、Enter/Tab/Esc、IME、取消、undo 和返回。
- 空、加载、无结果、失败、只读、索引未就绪、恢复状态。

标出哪些是 IDEA 已观测行为，哪些是 Taomni 适配或用户接受的差异。颜色、尺寸和快捷键从选定版本与平台获得，不硬编码某个平台的习惯为三端统一规则。先采用一组代表性主题/尺寸，再覆盖本次有变化的变体，避免无条件全组合矩阵。

## 原型与决策

已明确目标可以直接形成足够具体的图稿或现有组件试作。布局比较使用可查看静态图；操作反馈决定方案时再制作最小可交互原型。使用可用 `drawio`/浏览器工具时遵守其 skill。无需为每张小卡重建独立 HTML，也不把截图轮播当作等效交互。

用户已经授权 UI 重构，不再为“是否允许改变现有界面”提问。对实质未定取舍才请求用户选择：例如要偏离 IDEA、破坏兼容数据、替换编辑器内核或改变产品能力范围。有明确参照且在授权范围内的尺寸、对齐、组件拆分由 agent 自主决定。原型可审阅，原型通过不代表产品验收通过。

## 验收

使用 [视觉与交互验证](../../qa-ui-auto/references/idea-visual-interaction.md)：在相同 fixture/状态下比较 IDEA 参照与实际 Taomni UI，分别记录视觉、交互和功能结果。局部浏览器验证快速迭代；稳定后的本轮代表性 WebView 检查与真正受影响的 OS 场景集中执行。不能为避免编译把浏览器结果写成 native，也不能只验证后端正确就声称 UI 对齐。
