# UI 与交互对齐

用户已授权重构数据库会话的 UI：布局、组件拆分、菜单、面板、对话框和交互状态机都可以改，不再为“是否允许改界面”提问。复用现有组件是成本判断，不是约束。大改按可独立验收的用户场景分卡交付，每一步保持会话可用、数据可恢复。

## 目标描述

从参考包提炼本场景适用项，不凭记忆设计：

- 布局：导航器 / 编辑器 / 结果面板的分区与比例，结果面板标签、工具栏、状态栏（行数、耗时、事务状态）。
- 密度：树行高、网格行高与列宽、字体、图标、边距、溢出与截断。
- 状态：空、加载中、执行中（可取消）、无结果、错误（含错误定位）、只读、已修改未保存、未提交事务、断线重连。
- 交互：鼠标与快捷键入口、焦点在树/编辑器/网格间的转移、Enter/Tab/Esc、单元格编辑提交与取消、确认对话框、撤销。
- 快捷键从目标版本与平台实测获得，不把单一平台习惯写成三端规则；与 Taomni 全局快捷键冲突时在 spec 中裁定。

每项标注：DBeaver 或 DbVisualizer 已观测 / Taomni 适配（如无边框窗口、Tab 体系、AI 入口）/ 用户接受的差异。

## 取长规则

每个矩阵场景和 P1 spec 都写一行“参照决策”：`主参照: dbeaver|dbvis|merge|taomni`，外加理由和被放弃的一方做法。

1. 两款都实测后再选；只有一方有观测时，写“单侧参照”，另一方记为未观测，不推断。
2. 按用户结果取舍，依次看：数据安全（确认/预览/回滚更完整者）→ 完成任务的步数与焦点跳转 → 信息密度与可发现性 → 与 Taomni 现有 Action/快捷键体系的一致性。
3. `merge` 只在两者的优点互不冲突时使用（例如 DBeaver 的结果集面板结构加 DbVisualizer 的 “Copy Selection as IN clause”），并逐项列出来源。同一控件不混用两套交互模型。
4. 快捷键默认沿用主参照在当前平台上的实测绑定；与 Taomni 全局快捷键冲突时在 spec 中裁定。
5. 两款都不适用时标 `taomni`（Taomni 适配），沿用两者共有的通用规范。

## 需要用户决定的情况

只有实质取舍才询问：同时偏离两款参照的产品方向、破坏已保存数据兼容、改变能力范围（如引入 ER 图）、跨引擎行为无法统一。尺寸、对齐、组件拆分等有参照的细节由 agent 决定。

## 原型与验收

明显结构变化在 spec 中附静态图稿（drawio 或现有组件试作截图）；交互方案存疑时才做最小可交互原型。原型通过不等于产品验收。

验收按 [视觉与交互验证](../../qa-ui-auto/references/idea-visual-interaction.md) 的方法，把参照替换为本场景的主参照（DBeaver 或 DbVisualizer）：同一 fixture 与状态下分别记录视觉、交互、功能结果。browser 用于快速迭代；数据库效果与 OS 边界用 `live-db` / `native`。只验证后端正确不能声称 UI 对齐。
