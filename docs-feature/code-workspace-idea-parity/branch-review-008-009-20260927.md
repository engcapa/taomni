## 确认的问题（按严重性）

### S1 — sol，P1：嵌套仓库 diff 的 Edit 打开了另一个文件

工作区根为 `parent/`，含 `repo-a/`、`repo-b/`，同时存在 `parent/same.txt` 与 `parent/repo-b/same.txt`。打开 repo-b 的 `same.txt` diff，点击 Edit，实际打开的是 `parent/same.txt`。

新增的 `MainLayout.tsx:2226–2242` 找到了父工作区 root，却直接把 repo-relative 的 `path` 填入 root-relative 的 `CodeWorkspaceFileRef`；缺少 `repoRoot → sourceRoot.path` 的相对路径换算。这是本分支新增代码的问题。用户继续编辑/保存会作用于错误文件；本轮仅用临时 fixture 证明错误导航，未对任何个人文件做写入。

真实 native 观察：diff 包含 `repo-b WORKTREE`；点击 Edit 后编辑器显示 `OUTER FILE MUST NOT OPEN`，资源键为 `root:parent:same.txt`。预期应为 `root:parent:repo-b/same.txt`。

证据：[result.json](D:/code/person/taomni-parity-sol-review/qa-ui-auto-report/branch-review/sol-edit/result.json)、[错误编辑器截图](D:/code/person/taomni-parity-sol-review/qa-ui-auto-report/branch-review/sol-edit/wrong-editor.png)、[点击前 diff](D:/code/person/taomni-parity-sol-review/qa-ui-auto-report/branch-review/sol-edit/repo-b-diff.png)。现有 sol 用例以两个仓库直接作为 workspace roots，掩盖了此情况。

### S2 — sol，P2：只读 Git 查询改写 index，008-A3 不成立

在真实临时 Git 仓库提交 `stable.txt`，只改 mtime、保持内容不变，再通过真实 IPC 调用 `git_snapshot` 和 `git_operation_state`。sol 的 `.git/index` SHA-256 改变，工作区状态却仍为空；当前分支同条件 hash 不变。

sol 沿用会刷新 stat cache 的 status/conflict 探测；当前在 `git.rs:2216/2266` 使用 `ls-files --unmerged -z` 和 `GIT_OPTIONAL_LOCKS=0`。这是 sol 未补齐的既有问题，不能说是 sol 新引入。改写的是 index stat 数据，本轮未发现 commit 或暂存内容损坏，因此不升级成 P1 数据丢失。

### S3 — sol，P2：In Project 静默截断，漏掉真实 Java 命中

`StructuralSearchPanel.tsx:50–60` 最多枚举 2,000 个文件，再筛选 Java；丢弃 `listed.truncated`。创建 2,001 个排在前面的 `.txt` 和尾部含 `println(42)` 的 `zzz.java`，native UI Text=42 显示 `0 results · tree-sitter-java`，没有任何不完整提示。独立 IPC 确认返回 2,000 条且不含 `zzz.java`。

这不是仅有超大 Java 项目才触发：非 Java 文件也占限额。结果不能被当作完整 In Project 搜索。

### S4 — sol，P2：合法 Java 空白/注释导致 AST 漏报

同一个文件放置三条合法调用：`System . out.println(42);`、`System.out.println(/* comment */42);`、`System.out.println(42);`。相同原生探针中，当前返回 3 条，sol 返回 1 条。

`structural_search.rs:135–137` 对 receiver 原文要求等于 `System.out`，并把 named children 数量直接当作参数数量；空白和 comment extra 因此影响结构匹配。两边都实际使用 AST，此问题不能描述成“sol 使用 regex fallback”。

### S5 — 当前，P2：搜索旧磁盘内容，与 dirty 编辑器不一致

磁盘为 `println(42)`，在 native 编辑器改为 `println(999)` 且不保存，再查询 Text=42，仍返回 1 条；编辑器和磁盘独立读取结果证明此时二者不同。sol 在同一操作下返回 0 条，正确使用了当前活动缓冲。

当前 `CodeWorkspaceTab.tsx:8840` 只传 rootId/path，`structural_search.rs:919` 只读取磁盘。结果导航/选区可因此落在已被编辑的旧位置。应明确支持 dirty buffer overlay，或在入口明确告知磁盘快照范围并防止误导导航；当前 UI 没有说明。sol 仅覆盖活动文件，也不能据此推断其全部未保存文件都被搜索。

### S6 — 当前，P2：不支持的文件编码被当成成功空结果

真实临时 UTF-16LE Java 文件含 `println(42)`，原生 `structural_search_run` 返回 `status=ok`、0 matches、0 scanned、`truncated=false`。`structural_search.rs:922` 遇到非 UTF-8 就 continue，没有 typed unavailable/error 或 skipped-files 说明。同类 read failure 也直接跳过；大于 2 MiB 的工作区文件被过滤，但后两类本轮仅做代码审查，未宣称全部复现。

### S7 — sol：稳定的共享焦点单测回归；native 用户影响尚未独立确认

`CodeWorkspaceTab.test.tsx` 的 `ED-PARITY-006 Replace in Files action focuses Replace text` 在批量和单独重跑均失败，实际焦点是 `structural-search-pattern`。当前同测试通过。sol 共享 `searchFocusNonce`，且 `StructuralSearchPanel.tsx:123` 无 active 判断地 focus/select，是直接代码原因。

这是确定的回归测试失败，但隐藏元素在真实 WebView 中的 focus 行为可能与 jsdom 不同，因此不据此额外计一个已复现 native P1。
