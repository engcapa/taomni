# 大文件夹已读、列表批量操作及 Sent 副本反馈

日期：2026-10-17。用户已运行合并了上次响应性修复的新版。

后续更新：本文“只分析”的存储/备份结论记录的是 `cd6655e2` 阶段。用户随后明确要求完整邮件存储、独立目录、可选邮件备份及多实例协调，现已实现；最新行为和验证见 [邮件完整存储与可选备份](../docs-feature/mail-complete-storage-design.md)。下文保留原始诊断依据，不代表新实现仍有这些存储缺口。

## 原因和处理

1. **整个文件夹标记已读时 Connection Lost**：旧实现把所有本地未读 UID 用逗号连接为一条 STORE，无命令长度上限，重连重试仍发送同一超长命令。在限制命令为 4096 字节的 loopback IMAP 服务上，33,913 封邮件稳定复现 `IMAP UID STORE \Seen failed: Connection Lost`。这是已证明的客户端缺陷；没有抓取用户真实服务器的数据包，不能将所有 Connection Lost 都归为这一原因。
   - 整个文件夹先查询服务器 UNSEEN，涵盖尚未同步到本地的历史邮件。
   - 每批最多 250 个 UID，十位稀疏 UID 也保持在命令长度上限之内；批间释放连接锁，让交互请求有机会执行。
   - 对幂等 STORE 的断连只重连重试当前批次；每个成功批次提交本地事务。失败保留已经完成的部分，返回进度和错误，界面重新读取缓存。
   - 结束后核对服务器未读集合和数量，纠正其它客户端已读而本地仍未读的记录，不把稍后到达的邮件无条件归为已读。
2. **批量删除难发现**：原来已有复选框、右键删除和 Delete 快捷键，但直接点击邮件只打开阅读器，不支持 Ctrl/Cmd、Shift 多选，缺少明显的批量操作入口。
   - 增加 Ctrl/Cmd 点击切换、Shift 范围选择、Shift 点击复选框、列表内 Ctrl/Cmd+A、Escape 清空选择。普通点击/键盘导航选择单封，再用 Ctrl/Cmd 追加选择。
   - 增加 `Delete selected` 按钮、选中数量及选中行背景；全选作用于当前显示的行，折叠会话的隐藏子邮件不被悄悄选中。
   - 使用现有删除语义：普通文件夹移入 Trash；没有 Trash 或已在 Trash 中时，永久删除须确认，可取消。
   - 批量移动、复制、删除和标签操作按文件夹再按 250 封分批。完成一批更新一批，失败时保留尚未完成的选择。
   - 修复搜索结果只显示勾选却未计入操作目标的问题；跨文件夹或未加载页面的搜索结果可以读取和批量处理，标记、删除后同步更新搜索行。
3. **TC-MAIL-SEND-01 三平台丢失副本提示**：副本成功事件可先于发送 IPC 响应到达；旧界面随后把“copy saved to Sent”覆盖为“Message sent”。已在挂载测试中复现“事件先到失败、后到通过”。
   - 副本成功/失败使用独立、可关闭的提示，不再受 SMTP 接受结果及邮箱刷新状态覆盖。
   - 原用例继续断言真实 Sent 副本与 Drafts 删除，并增加刷新后提示仍存在的断言；不通过延长等待或删除断言掩盖竞态。

## 同时处理的性能瓶颈

- 标记已读、星标/标签、移动、删除缓存曾在异步函数中直接执行 SQLite 和等待数据库锁。改为阻塞线程池，保留公共异步工作线程给终端和网络 I/O。
- 标记/移除大量缓存记录原来每封单独自动提交。改为每批事务，复用 SELECT/UPDATE/DELETE 预编译语句，减少磁盘提交和 SQL 编译次数。
- 本地全文搜索及 POP3 的本地搜索回退原来运行于异步工作线程；现在也使用后台数据库任务。
- 临时磁盘库对照：相同的 3,000 行、SQL 和 SQLite DELETE journal，逐封自动提交三次为 15,743.09 / 14,025.54 / 35,817.93 ms；每 250 封一个事务为 107.46 / 92.68 / 203.35 ms，提交次数由 3,000 降至 12。保留所有样本；测试机同时有其它负载。这只测 SQL 提交开销，不能等同于整应用、终端或真实邮件服务的加速比例。
- 未更改邮箱代理配置或路由策略；这些修复不声称消除远端邮箱限流或真实网络延迟。

## 本地存储与备份：只分析，未修改备份行为

| 内容 | 实际存储 | 备份覆盖 |
| --- | --- | --- |
| 邮件 session 设置 | 主应用会话配置，凭据按现有会话/凭据机制处理 | Core/Full 中的会话及凭据范围 |
| 邮件缓存 | 每个 session 独立 `<app_data>/mail-cache/<session 清理名>-<SHA256 前16位>.db`，不是主 `taomni.db` 内的邮件表 | Full 包含；Core 默认不含；后端 custom 的 `includeMail=true` 包含 |
| 邮件头及状态 | 独立库内的文件夹、UID/同步水位、主题、地址、时间、标记、摘要、附件元数据、全文索引 | 随邮件库 |
| 正文 | 已抓取的纯文本/HTML 在库内 `body_text/body_html`；HTML 可含转换后的内嵌 CID 图片 | 仅已缓存正文随库，未抓取正文不在备份中 |
| 普通 IMAP 附件内容 | 默认按需从服务器读取；开启 attachmentCache 后，已打开/下载的附件写入 `mail-cache/attachments/<account>/<folder>/<uid>-<part>.bin` | 当前备份不递归收集这个目录，因此不包含附件缓存文件 |
| 用户另存的附件、EML | 用户选择的文件或配置的 saveDirectory；配置目录不是全邮箱镜像，部分正文读取和大邮件策略不保证每封都有完整 EML | 当前邮件备份不包含这些外置文件 |
| 草稿、模板、Outbox、联系人、过滤规则、日历数据 | 对应独立邮件库的表；草稿附件存路径/元数据，不嵌入附件字节 | 数据库记录随库；原附件文件需要独立保留 |
| POP3 本地原始邮件 | `mail_local_raw.raw` 保存完整 MIME BLOB，包括原始附件；UIDL 表记录下载状态 | 原始邮件在库内，因此选择邮件库时包含这部分 |

缓存默认保留全部邮件头（按天及数量上限为 0），正文默认保留最近 200 封/文件夹，实际受账号设置和裁剪时机影响。正文抓取默认初始上限 256 KiB；大邮件可按 MIME 部分补抓正文，仍不是保证保存所有完整原始邮件和附件。

备份实现依据：`backup/engine.rs::resolve_scope_flags` 的默认 Core 不含 mail；Full 含 mail。邮件收集只遍历 `mail-cache` 第一层 `.db`。本地备份和云端快照共用此收集逻辑。

另一个分析发现：主库/笔记库用 `VACUUM INTO` 取得一致性副本，但邮件库目前直接加入归档文件列表，没有逐库快照或数据库锁，也没有收集 WAL。同步写入时，不能把 Full 解释为有一致性保证的完整邮箱备份。此项按用户要求只分析并记录，未改动备份实现。
